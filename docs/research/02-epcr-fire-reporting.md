## 1. NEMSIS (EMS data standard)

### 1.1 Version status (as of late 2026)
- **v3.5.1 is the current release.** It was finalized and published by the NEMSIS TAC as build `3.5.1.250115` (January 15, 2025). **[C]** Sources: [v3.5.1 ChangeLog](https://nemsis.org/wp-content/uploads/2025/01/v3.5.1.250115-ChangeLog.pdf), [NEMSIS development timeline 10-24-25](https://nemsis.org/wp-content/uploads/2025/11/NEMSIS-development-timeline-10-24-25.pdf)
- **Compatibility:** v3.5.0 and v3.5.1 are backward-compatible. Per the NEMSIS versioning plan, a v3.5.0 document is valid under v3.5.1, but a v3.5.1 document may not be valid under v3.5.0. A translation package converts v3.5.1 to v3.5.0 (CP4). **[C]** Source: [v3.5.1 to v3.5.0 translation doc](https://nemsis.org/media/nemsis_v3/release-3.5.1/Translation/v3.5.1%20to%20v3.5.0/documentation.docx)
- **New in v3.5.1 (examples):** ePatient.23 Name Suffix, ePatient.24 Preferred Language(s), eVitals.34 Stroke Scale Score, dRecord.01–03 (software info), dAgency.27 Licensed Agency, international phone format, and some code-list removals (e.g., in eExam.16). The EMS dataset has about 14 changed items. **[C]** Same sources. A First Due release note also mentions **ePatient.25 "Patient's Sex"**, added because NEMSIS deprecated the gender terminology. **[P]** Source: [First Due ePCR release notes June 2025](https://support.firstduesizeup.com/portal/en/kb/articles/epcr-release-notes-june-2025)
- **Testing:** The NEMSIS TAC now tests vendors **only on v3.5.1**. Passing v3.5.1 effectively certifies v3.5.0 too. **[C]** Source: [NEMSIS Vendor FAQ (May 2026)](https://nemsis.org/wp-content/uploads/2026/05/NEMSIS_FAQ_VENDOR.pdf)
- **No single national sunset date for v3.4.** In 2026, states were still submitting a mix of v3.4, v3.5.0 and v3.5.1 data to the national repository. **[C]** Sources: [NEMSIS Activity Report Feb 2026](https://nemsis.org/wp-content/uploads/2026/03/NEMSIS-Activity-Report-February-2026.pdf), [May 2026](https://nemsis.org/wp-content/uploads/2026/07/NEMSIS-Activity-Report-May-2026.pdf)
  - California (CEMSIS/EMSA): v3.5 and v3.5.1 are accepted through **Oct 31, 2026**; **only v3.5.1 from Nov 1, 2026**. This date was postponed from Jan 1, 2026. **[C]** Sources: [OC-MEDS notice](https://www.ochealthinfo.com/sites/healthcare/files/2025-10/%235648%20OC-MEDS%20PCRS%20Update%20-Transition%20to%20NEMSIS%20v3.5.1.pdf), [San Diego County EMCC 9/2025](https://www.sandiegocounty.gov/content/dam/sdc/ems/3%20CEMSIS%20Update%20EMCC%209%202025.pdf)
  - Another jurisdiction (unidentified, per a Memorial Health doc dated June 2026) set a v3.5.1 deadline of Sept 1, 2026, after which v3.4.0 is rejected. **[P]** Source: [memorial.health PDF](https://memorial.health/Resources/89f67497-4c1a-49f0-9eae-7d5a22f21ff7/NEMSIS-%203.5.1-June-2026.pdf)
  - State transition checklists for vendors exist, e.g. Georgia's ([3rd-party vendor checklist](https://dph.georgia.gov/document/document/nemsis-v35-transition-checklist-3rd-party-epcr-vendor-software-systempdf/download)) and Wisconsin's ([ems-nemsis-v3.5.pdf](https://www.dhs.wisconsin.gov/ems/ems-nemsis-v3.5.pdf)).
- **Next version:** NEMSIS timelines list v3.6.0 and v3.6.1, but I found **no published calendar dates** for v3.6. **[P]** Source: [NEMSIS development timeline 1-12-23](https://nemsis.org/wp-content/uploads/2023/01/NEMSIS-development-timeline-1-12-23.pdf)
- National repository maintenance in 2026: reset to v3.5.0 CP5 / v3.5.1 CP1 in Jan 2026, with CP6/CP2 planned for April 2026. Builds therefore have **"critical patch" (CP) sub-versions**, and software must track them. **[C]** Source: Activity reports above.
- **Implication:** Build natively on v3.5.1. Store the NEMSIS version and schema build per record. Support down-translation to v3.5.0 for states that have not moved. v3.4 export is optional and legacy-only; only a few states still accept it, and that support is fading. Design the element registry to be version-driven (data-dictionary-as-config) so v3.6 can be added later.

### 1.2 Data model structure
- **Three datasets:** **EMSDataSet** (the ePCR, one per patient encounter), **DEMDataSet** (agency demographic/configuration: personnel, vehicles, facilities, configuration), and **StateDataSet** (state-defined value lists, custom elements, facilities and so on, published by the state). **[C]** Source: [NEMSIS v3.5.0 Data Dictionary overview](https://nemsis.org/media/nemsis_v3/release-3.5.0/DataDictionary/PDFHTML/EMSDEMSTATE/overview.html), [EMSDataSet Guide (2026)](https://nemsis.org/wp-content/uploads/2026/04/NEMSIS_V3_EMSDataSet_Guide.pdf)
- **EMSDataSet sections** (from the dictionary; the section list is standard but this run confirmed only part of it): eRecord, eResponse, eDispatch, eCrew, eTimes, ePatient, ePayment, eScene, eSituation, eInjury, eArrest, eHistory, eNarrative, eVitals, eLabs, eExam, eProtocols, eMedications, eProcedures, eAirway, eDevice, eDisposition, eOutcome, eCustom(Results), eOther. **[P]** Examples confirmed in sources: eRecord.01 (PCR Number), eResponse.03 (Incident Number), eTimes.12 (Destination Patient Transfer of Care), eVitals.01 (Vitals Date/Time). Source: [Requisite National Elements EMS DataSet](https://nemsis.org/wp-content/uploads/2025/01/NEMSIS-v3.5-Requisite-National-Elements-EMS-DataSet.pdf)
- **DEMDataSet sections** (dAgency, dContact, dConfiguration, dLocation, dVehicle, dPersonnel, dDevice, dFacility, dCustomConfiguration, dCustomResults, dRecord): **[U]** list from background knowledge; dRecord and dAgency.27 are confirmed as new in v3.5.1.
- **Element attributes [U, but well known in NEMSIS]:** Each element has a **Usage** (Mandatory / Required / Recommended / Optional) and a **National** flag (national vs state element). It also has nullability: **NOT values** (Not Applicable, Not Recorded, Not Reporting) and **Pertinent Negatives** (e.g., "Refused", "Unable to Complete", "Contraindication Noted", "Exam Finding Not Present") on specific elements. NEMSIS 3.5 changed some PN/NV rules (e.g., eDisposition.12 was removed and replaced by a set of new disposition elements: [NJ NEMSIS 3.5 Instructions](https://www.nj.gov/health/ems/documents/ems_data/NEMSIS%203.5%20Instructions.pdf), [Texas key changes](https://www.dshs.texas.gov/sites/default/files/injury/EMST-Registries/PDF/NEMSIS-v3-5-Key-Changes.pdf)). **[P]**
- **Data model implication:** Each element needs (value | NV | PN), plus a correlation ID, plus timestamps. Repeating groups (vitals, meds, procedures) need stable per-row UUIDs for sync and for the NEMSIS `CorrelationID`.

### 1.3 National vs state vs custom elements
- **National elements** are sent to the national repository. **State elements** are a superset defined by each state and collected by the state repository. **[C]** Source: [Requisite National Elements doc](https://nemsis.org/wp-content/uploads/2025/01/NEMSIS-v3.5-Requisite-National-Elements-EMS-DataSet.pdf), [Illinois "why" doc](https://dph.illinois.gov/content/dam/soi/en/web/idph/files/why---il-nemsis-elements-final.pdf)
- **Custom elements:** States define them in the StateDataSet (`sCustom...`/`eCustomConfiguration.01–.0x`, title, definition, data type, allowed values). Agencies can also define custom elements (`dCustomConfiguration`). Values travel in `eCustomResults` / `dCustomResults`. **[P]** The Arizona translation doc confirms eCustomConfiguration.02 (title) and .03 (definition) under StateDataSet: [AZ V3.4 to V3.5 Translation](https://www.azdhs.gov/documents/preparedness/emergency-medical-services-trauma-system/data/PIERS/V3.4-to-V3.5-Translation-Documentation.pdf). The dCustom naming is **[U]**.
- States also publish their own **schematron** (business rules), **custom value lists** and **facility code lists** that vendors must load. Georgia requires vendors to "correctly apply the Schematron file, validation rules, custom data elements, and facilities codes". Alabama requires passing the Alabama Schematron plus a successful upload to the state repository. **[C]** Sources: [Georgia vendor presentation](https://dph.georgia.gov/document/document/oemst-nemsis-35-presentation-epcr-vendorspdf/download), [Alabama NEMSIS vendors](https://alabamapublichealth.gov/ems/nemsis-vendors.html), [AL software compliance](https://www.alabamapublichealth.gov/ems/assets/al-nemsis-software-compliance.pdf)
- Some states have extensive "essential element" books, e.g. California CEMSIS ([Sacramento CEMSIS Essential Elements Book](https://dhs.saccounty.gov/PUB/EMS/Documents/Technical%20Advisory%20Group/2024%20TAG/CEMSIS%20list%20%26%20Essential%20Elements%20Book%20_%20December%202023%20Release%20..pdf)). LA County even keeps its own field manual ([LA County EMS Report Form manual](https://file.lacounty.gov/SDSInter/dhs/1021588_EMSReportFormInstructionManual.pdf)).
- **How vendors handle per-state sets [P/U]:** The common pattern is to ingest the state's **StateDataSet XML** (value lists, custom elements, facilities) and **state schematron**, and then layer **agency configuration** (DEMDataSet plus agency custom rules) on top. Elements are then shown or required according to the merged rule set. Vendors such as First Due advertise "built-in validation for NEMSIS and state data" ([First Due ePCR](https://firstdue.com/products/epcr)).
- **Architecture implication:** Use a **three-layer configuration model: national, then state, then agency (then optionally county/region, as with California LEMSAs)**. Each layer adds elements, value lists, validation (schematron) and required-ness. It needs to be versioned and effective-dated, because states change their sets mid-year.

### 1.4 Schematron validation
- NEMSIS validation has two levels: **XSD** (structure/types) and **Schematron** (business rules, with severities). The NEMSIS Schematron guide (v3.4) describes ISO Schematron processed with **Saxon (XSLT 2.0)**. **[C]** Source: [NEMSIS V3 Schematron Guide](https://nemsis.org/media/nemsis_v3/release-3.4.0/Schematron/documentation/NEMSIS_V3_Schematron_Guide.pdf) (v3.4; I did not find a v3.5-specific guide).
- National schematron plus state schematron results are returned with severity levels (fatal/error/warning) **[U for exact levels]**, and fatal errors can cause rejection.
- **Implication:** Run the **official .sch rules (compiled to XSLT)** server-side as the source of truth. Mirror the critical rules in a client-side rule engine so validation works offline in the tablet UI. Keep validation results per record for QA dashboards. Re-implementing schematron by hand is a known drift risk, so prefer executing the real files (e.g., SaxonJS in the client, Saxon-HE on the server). **[Design recommendation]**

### 1.5 State data submission (web services)
- NEMSIS V3 web services are **SOAP over HTTPS**, with standard WSDL operations **SubmitData, RetrieveStatus, QueryLimit**, and all NEMSIS-compliant implementations must support them. Submissions specify a dataset type (EMSDataSet / DEMDataSet / StateDataSet) and schema version. Status codes are defined in the whitepaper. **[C]** Source: [NEMSIS V3 Web Services whitepaper](https://nemsis.org/media/nemsis_v3/master/WSDL/NEMSIS_v3_WebServices.pdf)
- A state example is Texas EMSTR: a SOAP `SubmitData` request with organization ID and password, swapping the endpoint for production. Source: [Texas DSHS EMSTR Webservices Tech Guide 3.5](https://www.dshs.texas.gov/sites/default/files/injury/EMST-Registries/PDF/DSHS-EMSTR-Webservices-TechGuide-3-5-Jan2024.pdf). Other state repositories document SOAP endpoints too (e.g., myCARES: [SOAP info](https://mycares.net/sitepages/soapinfo.jsp)).
- Many states run **ImageTrend** state repositories, and some states give agencies free Elite (e.g., Montana: [MT EMS Data](https://dphhs.mt.gov/publichealth/EMSTS/EMS/EMSData)). Third-party vendors submit into those repositories via SOAP.
- **Implication:** You need a submission service with a per-state endpoint/credential registry, async queue, retries, `RetrieveStatus` polling and storage of validation reports, plus a resubmit-on-edit workflow (an amended PCR needs resubmission). State deadlines for submission vary (often within days of the call) **[U, varies by state]**.

### 1.6 Compliance testing and certification for software vendors
- **Two tracks:** "**Collect Data**" (the ePCR software; the TAC provides test cases that the vendor enters and exports) and "**Receive and Process**" (state/repository software; the TAC sends files that must be processed unaltered). **[C]** Sources: [Compliance Process – Collect Data](https://nemsis.org/media/nemsis_v3/release-3.5.0/Compliance/NEMSIS%20V3%20Compliance%20Process%20-%20Collect%20Data.pdf), [Receive and Process](https://test.nemsis.org/media/nemsis_v3/release-3.5.0/Compliance/NEMSIS%20V3%20Compliance%20Process%20-%20Receive%20and%20Process.pdf)
- **Renewal:** retest every **2 years** (states may require yearly). Testing must be completed within **90 days** of the application. After a major version, vendors must test on the latest version. For minor versions, testing begins the year after release. **[C]** Sources: [NEMSIS Compliance FAQ](https://nemsis.org/wp-content/uploads/2026/05/NEMSIS_FAQ_COMPLIANCE.pdf), [NEMSIS V3 Compliance Policy](https://nemsis.org/wp-content/uploads/2024/06/NEMSIS-V3-Compliance-Policy.pdf)
- **State-level vendor approval** comes on top of this: state schematron, a test upload to the state repository, and sometimes a state-specific checklist (GA, AL, above). First Due publicised achieving "NEMSIS 3.5 Receive & Process compliance" for its State EMS Data Repository product ([First Due news](https://www.firstdue.com/news/nemsis-3-5-compliance)).
- **Implication:** Budget **NEMSIS Collect Data certification on v3.5.1** before selling to any EMS agency. That is a gating item; plan on roughly 90 days of testing plus state-by-state onboarding.

## 2. Fire reporting: NFIRS to NERIS

### 2.1 Status/timeline (as of Nov 2026)
- **NFIRS is decommissioned.** From Jan 1, 2026 all fire incident reporting goes through **NERIS** exclusively. 2025 incidents could go to either system, and NFIRS became unavailable to all users in **February 2026**. **[C]** Sources: [USFA NFIRS Sunset](https://www.usfa.fema.gov/nfirs/sunset/), [USFA NFIRS data page](https://www.usfa.fema.gov/data-insights/nfirs/)
  - State-level dates differ slightly: Texas required all NFIRS data (including 2025) by Jan 31, 2026, with NFIRS gone Feb 22, 2026 ([TDI NERIS resources](https://agate.tdi.texas.gov/fire/neris.html)). Michigan ended new NFIRS incidents Jan 15, 2026 and updates Jan 31, 2026 ([Michigan NERIS](https://www.michigan.gov/lara/bureau-list/bfs/nfirs/neris), [MI FAQ](https://www.michigan.gov/lara/-/media/Project/Websites/lara/bfs/NFIRS/NERIS-and-NFIRS-FAQ-11262025.pdf)). Virginia: NERIS reporting is mandatory for AFG/ATL grants from June 1, 2026 ([VDFP NERIS](https://www.vdfp.virginia.gov/risk-reduction/neris/)). **[C]**
- USFA reports NERIS passed **15 million** all-hazards reports ([USFA media release](https://www.usfa.fema.gov/about/media-releases/neris-surpasses-15-million-in-all-hazards-reporting/)). **[C]**
- **Pain in the field:** Many departments' RMS vendors were not NERIS-ready. Some departments have a backlog of 2025–26 calls never filed, and some never created their own NERIS account (every department needs one). State funding can be tied to reporting compliance. These claims come mainly from vendor blogs and should be treated as anecdotal. **[P]** Sources: [Alpine "Behind on NERIS"](https://alpinesoftware.com/neris/behind/), [Lexipol](https://www.lexipol.com/resources/blog/the-switch-from-nfirs-to-neris-is-here/)
- **Implication for SomaOS:** NFIRS 5.0 export is now **legacy only** (historic data import/migration). **NERIS is mandatory day one** for any fire RMS module. A "catch-up/backfill" workflow (bulk submit of past incidents) is a selling point.

### 2.2 NERIS data model
- NERIS is developed by **FSRI (UL Research Institutes' Fire Safety Research Institute)** for USFA. Public **Core data schemas** have been released (beta first), including an object-relational model for dispatch and incident data. A **CAD interface schema** is in progress. **[C]** Sources: [FSRI NERIS core schemas beta](https://fsri.org/program-update/neris-core-data-schemas-released-beta), [USFA NERIS data FAQ](https://www.usfa.fema.gov/nfirs/neris/faq/data/)
- **Modules/sections mentioned in sources:** Core (incident, dispatch, units/response), **Fire**, **Medical**, **Rescues/Casualties**, **Hazardous situations (HAZSIT)**, Risk Reduction (e.g., smoke alarms, sprinklers), firefighter/responder documentation, animal rescue, **Actions & Tactics** (replacing NFIRS action codes, including contamination-reduction tactics), and simplified **exposures**. Investigations and Exposures schemas are planned in future releases. **[P]** Sources: [NDSU NERIS transition guide](https://www.ndsu.edu/sites/default/files/documents/NERISTransitionGuide.pdf), [Wisconsin NERIS briefing](https://dsps.wi.gov/Documents/Programs/FirePrevention/NERISEducationalBriefing.pdf), [USFA data FAQ](https://www.usfa.fema.gov/nfirs/neris/faq/data/)
- **Incident types:** These use a hierarchical `CATEGORY||TYPE||SUBTYPE` code (e.g., `HAZSIT||HAZARD_NONCHEM||…`). There are fewer types than NFIRS, and **up to 3 incident types per incident** are allowed. **[C]** Sources: [Oklahoma NERIS presentation](https://www.oklahoma.gov/content/dam/ok/en/fire/documents/NERIS%20OK%20Presentation%209.28.25.pdf), [Maine plus-one codes](https://www.maine.gov/dps/fmo/sites/maine.gov.dps.fmo/files/inline-files/NERIS%20plus-one%20codes_updated_8_28_26_0.pdf)
- **State extensions:** Some states define **"plus-one" codes** layered on NERIS (Maine), so a per-state extension mechanism is needed for fire as well as EMS. **[C]** Source: Maine plus-one codes above.
- **Crosswalks:** NFIRS-to-NERIS crosswalks exist (e.g., [Oregon OSFM crosswalk](https://www.oregon.gov/osfm/about-us/Documents/NFIRS-NERIS-Crosswalk.pdf)) and are useful for migrating historic NFIRS data.
- **Medical in NERIS:** Medical incidents are categorized as injury / illness / other, with more detailed types than NFIRS. **[C]** Source: USFA data FAQ. **Implication:** A combined fire+EMS response needs both a NERIS incident (fire department obligation) and a NEMSIS PCR (EMS obligation) linked to the same CAD incident, entered once and mapped to both.

### 2.3 API / integration / vendor onboarding
- The **NERIS API** is RESTful and defined by an **OpenAPI** schema (Swagger docs are published). It is written in Python. Auth uses **client ID + client secret** (OAuth2-style client credentials). **[C/P]** Source: [NC OSFM Incident Reporting & RMS page](https://www.ncosfm.gov/fire-rescue/nfirs-incident-reporting). The exact token flow, scopes and rate limits were **not confirmed [U]**.
- **Enrollment model:** The **vendor** has a Client ID. The **department admin** enrolls that vendor Client ID under "Enrollments/Integrations" in the NERIS portal, which grants that integration permissions for that entity. Admins can revoke it. **[C]** Sources: [ESO NERIS vendor enrollment QSG](https://www.eso.com/wp-content/uploads/2025/07/NERIS-API-VendorIntegrationEnrollmentQSG.pdf), [PA OSFC vendor activation](https://www.pa.gov/content/dam/copapwp-pagov/en/osfc/documents/reporting/neris%20agency%20vendor%20activation%20instructions.pdf), [Texas TDI](https://tdi.texas.gov/Fire/neris.html)
- **NERIS Compatibility Badge (vendor certification):** (1) build the integration; (2) submit a test incident to the **test environment**; (3) capture the incident number and submit an **update**; (4) create a station and add a unit to the "FSRI Fire Department" test entity. Passing vendors are listed at neris.fsri.org/integration-partners. **[C]** Sources: [Wisconsin NERIS briefing](https://dsps.wi.gov/Documents/Programs/FirePrevention/NERISEducationalBriefing.pdf), [USFA integrations FAQ](https://www.usfa.fema.gov/nfirs/neris/faq/integrations/)
- **Entity data:** NERIS models departments (entities), **stations and units**. The RMS must sync its station/unit roster to NERIS. **[C]** (inferred from badge step 4).
- **Implication:** The SomaOS fire module needs: a multi-tenant NERIS credential model (one vendor client ID, many department enrollments); entity/station/unit sync; incident create plus update (amendments); validation against the published OpenAPI/JSON schemas; retry/queue; and a submission status dashboard. Also apply for the compatibility badge early.

### 2.4 NFIRS 5.0 modules (legacy, for migration/history)
- Basic (NFIRS-1, mandatory for every incident), Fire (2), Structure Fire (3), Civilian Fire Casualty (4), Fire Service Casualty (5), EMS (6), HazMat (7), Wildland Fire (8), Apparatus/Resources (9), Personnel (10), Arson (11), plus Supplemental (1S) and Juvenile Firesetter. **[C]** Sources: [Utah NFIRS forms for modules](https://firemarshal.utah.gov/wp-content/uploads/NFIRS-Forms-for-Modules.pdf), [USFA NFIRS documentation](https://www.usfa.fema.gov/data-insights/nfirs/documentation/), [Illinois one-page reference](https://sfm.illinois.gov/content/dam/soi/en/web/sfm/sfmdocuments/documents/nfirs-onepagereferenceguidess.pdf), [Michigan tips](https://www.michigan.gov/documents/tipsonNfirs_8611_7.pdf)
- Which optional modules (EMS, HazMat, Wildland, Apparatus, Personnel) are required was decided **by each state**. **[C]**
- NFIRS 5.0 transaction file format spec: [NFIRS spec 2015](https://usfa.fema.gov/downloads/pdf/nfirs/nfirs_spec_2015.pdf).
- **Implication:** Import historic NFIRS data (for trend reports and ISO) using the 5.0 spec and the crosswalk. No new NFIRS submission is needed.

## 3. ePCR UX and integration requirements

### 3.1 Offline-first operation
- Offline capability is standard among leaders. **ImageTrend Elite Field** is the "offline data collection solution that does not require an internet connection", needing connectivity only to sync ([NJ Elite doc](https://www.nj.gov/health/ems/documents/ems-toolbox/nj_elite.pdf), [ImageTrend Elite spec](https://www.maine.gov/dps/fmo/sites/maine.gov.dps.fmo/files/inline-files/imagetrend-elite_specs_resized_2.pdf)). **[C]**
- Lack of offline support is a real complaint: an AngelTrack reviewer noted they "cannot reach AngelTrack without internet" ([Capterra AngelTrack](https://www.capterra.com/p/133126/AngelTrack/)). An ImageTrend G2 reviewer complained of "too many sync updates when logging in many times a day" ([G2 ImageTrend](https://www.g2.com/products/imagetrend/reviews)). **[C]**
- I found **no public documentation of vendor conflict-resolution strategies**. **[U]** Design recommendations:
  - Use a **single-writer lock per PCR** (the primary author's device), with crew members contributing to sub-collections (vitals/meds/procedures rows with UUIDs, append-only). Merge at row level, and use field-level LWW with an audit trail only for scalar fields. Supervisors/QA edit only after the PCR is posted/locked, which creates an addendum/amendment rather than an overwrite.
  - Keep a local encrypted store (SQLite/SQLCipher or IndexedDB with app-level encryption). Persist a full local outbox. Never discard an unsynced chart; show sync status on screen at all times. Support device-to-device handoff (e.g., transfer the chart to another crew member's tablet) through the server, or via a QR/local handoff when offline (advanced).
  - Cache config offline: state/agency element sets, value lists, schematron-derived rules, facilities and protocols, with versioning.
  - Remote wipe/MDM for lost tablets (HIPAA).

### 3.2 Cardiac monitor / vitals device integration
- **ZOLL (X Series, etc.):** Data flows **monitor to ZOLL cloud (RescueNet/"Case Review"/C2C)** and is then pulled by the ePCR vendor. AngelTrack's downloader pulls "Monitor", "Twelve-lead", "Defib" and "Treatment" snapshots, and 12-leads only appear if the crew pressed the 12-lead button. ([AngelTrack ZOLL C2C](https://support.angeltrack.com/help/zollc2c.htm)) **[C]** Third-party access is through the **ZOLL Development Partner Program (ZDPP)**: SDK, web API, docs and loaner devices ([ZDPP](https://www.zolldata.com/zdpp)). **[C]** ZOLL's own ePCRs (RescueNet ePCR, emsCharts) have tighter integration, e.g. the "RescueNet CaseReview link only available with emsCharts" ([ZOLL emsCharts](https://www.zolldata.com/fire-emscharts), [RescueNet ePCR overview](https://www.zolldata.com/hubfs/RescueNet%20ePCR/Brochures/RescueNet%20ePCR%20Product%20Overview.pdf)). Note the **competitive conflict**: ZOLL sells competing ePCRs.
- **Stryker (Physio-Control) LIFEPAK:** The monitor uploads the case to **LIFENET** (cloud), and the ePCR then imports matching cases, creating vitals and ECG records (12/15-lead, shock, NIBP snapshots). Stryker reps verify the devices and configure a service account ([AngelTrack Stryker](https://support.angeltrack.com/help/stryker.htm)). Vendors integrate server-to-server via the **LIFEPAK SDK** ([JEMS on LIFENET](https://www.jems.com/patient-care/physio-control-introduces-cloud-based-li/)). The **CODE-STAT** review software receives data through the same gateway ([Stryker LIFENET](https://stryker.com/us/en/emergency-care/products/lifenet-system.html)). **[C]**
- **Philips:** The HeartStart Data SDK (C#/.NET/XML, an old stack targeting Windows 7/XP) maps MRx and other device data into ePCRs ([Philips SDK page](https://www.philips.gr/healthcare/product/HCNOCTN91/-)). The **MRx is end-of-life in the US** (accessories ended Feb 2021), and a DOJ consent decree restricted Philips external defibrillator distribution in the US ([DOJ](https://www.justice.gov/opa/pr/district-court-enters-permanent-injunction-against-philips-north-america-and-two-executives), [MRx PMA letter](https://www.philips.com/c-dam/b2bhc/master/landing-pages/pma/mrx-pma-letter.pdf)). Tempus Pro was 510(k) cleared, but its current US status is **[U]**. **Implication: Philips is low priority in the US. Prioritize ZOLL plus Stryker.**
- ImageTrend notes monitor integrations "require special data sharing agreements" ([ImageTrend integration sheet](https://www.imagetrend.com/media/oe3dbjco/lit_integrationsolutions_6-23.pdf)). Industry commentary says manufacturers guard proprietary formats closely ([JEMS "Why can't we all get along"](https://www.jems.com/patient-care/why-can-t-we-all-get-along/)). **[C]**
- **Implication:** Monitor integration is **business-development gated** (partner agreements), not purely technical. Architecture: a "device case import" service that pulls from vendor clouds, matches cases to PCRs by device serial plus time window, and stages vitals/ECG/events for **crew review and acceptance** (no silent auto-insert; time-sync issues are common). It must store 12-lead PDFs/images as attachments and map them to eVitals and eProcedures (defib/pacing) and eDevice.

### 3.3 CAD integration
- CAD feeds should populate eResponse/eDispatch/eTimes (PSAP call, unit notified, en route, on scene, at patient, transport, at destination, transfer of care, back in service), the incident address and unit/crew. NERIS's CAD interface schema is in progress (USFA data FAQ above). **[P]**
- **Implication:** Use one canonical "Incident" object from CAD that spawns both a NERIS incident and N PCRs (one per patient). Record times from CAD versus crew edits with provenance (eTimes values from CAD should be flagged; edits should be audited).

### 3.4 Hospital / HIE exchange (HL7, FHIR)
- **SAFR model** (Search, Alert, File, Reconcile) from ONC and California EMSA is the reference framework. Search looks up patient history; Alert is the ED pre-arrival notification; File posts the PCR into the hospital EHR; Reconcile returns hospital outcomes to EMS for QA and billing. Barriers include patient matching, security and connectivity. **[C]** Sources: [HealthIT.gov SAFR profile](https://healthit.gov/resources/state-and-community-profiles-emergency-medical-services-ems-data-integration-to-optimize-patient-care-the-search-alert-file-reconcile-safr-model-of-health-information-exchange/), [Applied Clinical Informatics review](https://pmc.ncbi.nlm.nih.gov/articles/PMC6291398)
- **Standards:** HL7 CDA R2 "EMS Patient Care Report" (NEMSIS-sponsored, DSTU 2012, apparently not updated) ([HL7 CDA EMS Run Report](https://wiki.hl7.org/w/images/wiki.hl7.org/5/57/CDAR2L3_IG_EMSRUNRPT_DSTUR1_2012JUL_DEVELOPER.pdf)). **No finished US FHIR EMS IG was found.** IHE's mobile Paramedicine Summary of Care (mPSC) has a **NEMSIS-to-FHIR mapping** ([IHE mPSC NEMSIS mapping](https://build.fhir.org/ig/IHE/PCC.PCS/NEMSIS-Mapping.html)). Switzerland and the Czech Republic have FHIR EMS IGs (not US). **[C]**
- **Vendor HIE products:** **ZOLL Care Exchange** (cloud, HL7/CCD/FHIR, bi-directional) ([ZOLL HL7](https://www.zolldata.com/hl7), [ZOLL Care Exchange overview](https://www.zolldata.com/hubfs/ZOLL%20Care%20Exchange%20Solution%20Overview.pdf)). ESO's **Health Data Exchange** and ImageTrend's **Health Information Hub** were **not confirmed in this session [U]**, but ESO acquired an EMPI vendor, **Occam Technologies** (2022), and the ED analytics firm **d2i** (April 2026) for its "911 to post-acute" data pipeline ([HIT Consultant d2i](https://hitconsultant.net/2026/04/07/eso-solutions-acquires-d2i-emergency-department-ems-data-intelligence/), [Occam](https://www.healthcareittoday.com/2022/09/08/eso-acquires-occam-technologies-leading-provider-of-enterprise-master-patient-index-empi-solution/)). Pulsara (pre-arrival comms) integrates with ZOLL RescueNet and emsCharts ([Pulsara](https://www.pulsara.com/rescuenet)). **[C]**
- **Implication:** For v1, generate a **PDF plus a C-CDA/FHIR Bundle (IHE mPSC-aligned)** for hospital "File". For later releases, a FHIR R4 API for outcomes "Reconcile" (eOutcome elements) and an EMPI/patient matching service. Hospital interoperability is a differentiator, and ESO is investing heavily here.

### 3.5 PDF/print run report
- Universal requirement: a hospital drop-off copy (often abbreviated, a "transfer of care" report at the bedside) and a full PCR PDF for records requests and billing. **[U: standard industry practice]** Templates should be configurable per agency, with signatures embedded, version-stamped (amendments shown), and with the redaction needed for records-release workflows.

### 3.6 Narrative templates
- Common formats are **SOAP** (Subjective, Objective, Assessment, Plan), **CHART** (Chief complaint, History, Assessment, Rx/treatment, Transport) and **DCHARTE** (Dispatch, Chief complaint, History, Assessment, Rx, Transport, Exceptions). **[U: background knowledge, not verified this session; the search budget ran out]**
- Vendors offer **auto-generated narratives** from structured data (ZOLL RescueNet: "create editable, automated narratives", [RescueNet overview](https://www.zolldata.com/hubfs/RescueNet%20ePCR/Brochures/RescueNet%20ePCR%20Product%20Overview.pdf)), plus **AI dictation that maps to NEMSIS fields with mandatory human review** (First Due: [First Due ePCR](https://firstdue.com/products/epcr)). **[C]**
- **Implication:** Provide narrative generation from structured data, agency template choice (SOAP/CHART/DCHARTE), AI-assisted dictation with provenance flags, and a human-review gate.

### 3.7 Validation / protocol-driven required fields
- Required-ness = union of NEMSIS national + state schematron + agency rules + **protocol/impression-driven rules** (e.g., chest pain implies 12-lead required within X minutes; cardiac arrest triggers eArrest section; stroke triggers eVitals.34 stroke scale; refusal triggers refusal elements). **[P: the concept is standard; the specific examples are illustrative]**
- Protocol integration exists in the market: First Due + **OneDose** pushes medication/protocol actions in NEMSIS format into the ePCR ([First Due OneDose](https://www.firstdue.com/news/onedose-first-due-epcr-integration)). **[C]**
- **Implication:** A declarative rule engine (conditions on any element leading to required/visible/warning) that runs offline. Severity tiers: **block post**, **warn**, **QA flag**. "Sections" are revealed dynamically by impression/complaint.

### 3.8 QA/QI review workflows
- Typical flow: PCR posted, then auto-flags (rules and keywords), then reviewer queue, then comments/return to author, then addendum, then close. ESO reviewers asked for QM review lists auto-populated from procedures/impressions and complained that "chart review is too slow" ([G2 ESO EHR](https://www.g2.com/products/eso-ehr/reviews)). ImageTrend reviewers wanted better search and incomplete-vs-complete tracking ([G2 ImageTrend](https://www.g2.com/products/imagetrend/reviews)). **[C]**
- Device case review: ZOLL CaseReview / Stryker CODE-STAT for CPR quality. **[C]**
- **Implication:** Configurable QA triggers, reviewer assignment, protected QA (peer-review privilege; QA notes stored separately from the legal record) **[U: state peer-review statutes vary]**, CPR-quality metrics import, and dashboards of open charts by author.

### 3.9 Signatures
- **Patient refusal (AMA):** This needs capacity assessment documentation, risks explained, patient signature, **witness signature**, and the crew signature. It is the highest-liability chart type. **[U: standard practice; specific requirements are set by state/medical direction and were not verified]**
- **Medicare 42 CFR 424.36:** The beneficiary signature is required unless an exception applies. The (b)(1)–(4) authorized representatives can sign. The **(b)(6) exception** applies to emergency transports (later extended to non-emergency) when the beneficiary is physically/mentally incapable and no representative is available or willing. It requires: a contemporaneous **crew member statement** of the reason, plus the **receiving facility representative's** name, time and location of receipt (signed), **or** secondary documentation (facility registration/admission records). This must be retained **at least 4 years** from date of service. If the beneficiary refuses to authorize, Medicare cannot be billed (the beneficiary can be). **[C/P]** Sources: [eCFR 42 CFR 424.36](https://www.ecfr.gov/current/title-42/chapter-IV/subchapter-B/part-424/subpart-C/section-424.36), [Cornell LII](https://www.law.cornell.edu/cfr/text/42/424.36), [CMS signature guidance (2008)](https://webarchive.library.unt.edu/web/20080916034134/http://www.cms.hhs.gov/AmbulanceFeeSchedule/downloads/Guidance_on_Beneficiary_Signature_Requirements_for_Ambulance_Claims.pdf), [PWW EMS law](https://pwwemslaw.com/node/86), [Foley](https://www.foley.com/?p=58449). The exact current wording of (b)(6) was not fully retrieved, so verify against eCFR.
- **Implication:** The signature subsystem needs structured signature types (patient, authorized rep with relationship, crew "reason unable to sign" statement, receiving facility rep with name/time/location, witness, PCS signer), each with timestamp, device, GPS, signer name/role, and a hash of the document state at signing. Offline capture is required. Signatures should be immutable and bound to the PCR version.

### 3.10 Billing export
- Ambulance claims go on the **837P** (professional), with one base-rate line (e.g., **A0427 ALS1-emergency**, A0429 BLS-emergency, etc.) and one **mileage** line (**A0425** ground; A0435/A0436 air). Billing is for **loaded miles only**, to the tenth of a mile under 100 miles. **Origin/destination modifiers** must match the run report, or mileage is denied. Date of service is the date the loaded vehicle departs the pickup point. **[C]** Sources: [BCBS MN ambulance coding](https://bluecrossmn.com/sites/default/files/DAM/2023-10/Commercial-General-Coding-069-Ambulance-Services-10.24.23.pdf), [CMS ambulance transport reason codes](https://www.cms.gov/files/document/ambulance-transport-reason-codes-statements.pdf), [Noridian hospital-based ambulance guide](https://med.noridianmedicare.com/web/jfa/provider-types/ambulance/hospital-based-ambulance-billing-guide), [Idaho EMS Billing 101 (2026)](https://ems.idaho.gov/wp-content/uploads/2026/06/EMS-Agency-Billing-101.pdf)
- **PCS (Physician Certification Statement):** Required in advance for non-emergency scheduled transports. For **repetitive scheduled** transports it must be signed by the attending physician and dated no more than **60 days** before service. For unscheduled non-emergency transports, if the PCS can't be obtained within **21 days**, document the attempts and then bill. Bed confinement is one factor, not the sole test. RSNAT prior authorization applies (e.g., up to 40 round trips in 60 days before PA is needed, per 2026 CMS material). The regulation is **42 CFR 410.40** (the paragraph numbering changed from (d) to (e), so verify). **[C/P]** Sources: [eCFR 410.40](https://www.ecfr.gov/current/title-42/chapter-IV/subchapter-B/part-410/subpart-B/section-410.40), [CMS MLN ambulance compliance](https://www.cms.gov/training-education/medicare-learning-networkr-mln/compliance/medicare-provider-compliance-tips/ambulance-services), [CMS RSNAT PA model](https://www.cms.gov/files/document/mln6805343-repetitive-scheduled-non-emergent-ambulance-transport-prior-authorization-model.pdf), [Palmetto PCS](https://www.palmettogba.com/palmetto/rr.nsf/DID/8A5KUC2727)
- **Ambulance condition codes (medical necessity):** CMS publishes the transport reason code/statement list ([CMS PDF](https://www.cms.gov/files/document/ambulance-transport-reason-codes-statements.pdf)). Mapping clinical documentation to these codes is a key billing feature. **[C]**
- Many agencies outsource billing. Common integration patterns are a **NEMSIS XML export** to the billing company or vendor-to-vendor integrations (e.g., ZOLL Billing pulls from emsCharts, RescueNet ePCR and third-party ePCRs: [ZOLL Billing overview](https://zolldata.com/hubfs/ZOLL%20Billing/Brochures/ZOLL%20Billing%20Solution%20Overview.pdf)). **[C/P]**
- **Implication:** The data model must capture billing-grade data natively: loaded mileage (odometer or GPS, tenths), origin/destination type modifiers, level-of-service determination (BLS/ALS1/ALS2/SCT) derived from interventions, medical-necessity condition codes, PCS/ABN documents, insurance/face sheet capture (photo/OCR), and signature exceptions. Export as NEMSIS 3.5.1 XML plus an optional 837P generator later, or partner with billing companies.

## 4. Legal / compliance

- **HIPAA:** EMS agencies that bill electronically are covered entities. SomaOS would be a **business associate** and must sign BAAs (and flow BAAs down to its subprocessors: cloud, email/SMS, AI providers). **[U: standard HIPAA analysis]**
- **HIPAA Security Rule update:** The Jan 2025 NPRM would make **encryption at rest and in transit and MFA mandatory** (removing "addressable"), and adds asset inventory, etc. It is **not final**; the projected final action date slipped to **July 2027**, and the current rule remains in force. **[C]** Sources: [Fierce Healthcare](https://www.fiercehealthcare.com/health-tech/feds-push-back-hipaa-security-rule-overhaul-july-2027), [Holland & Knight (July 2026)](https://hklaw.com/en/insights/publications/2026/07/hipaa-security-rule-amendments-now-projected-for-july-2027). **Implication:** Build to the NPRM now (encryption everywhere, MFA, asset inventory, 72-hour restore, annual audits), since it is likely the bar procurement will ask for.
- **Audit logging:** The HIPAA Security Rule requires audit controls (45 CFR 164.312(b)) **[U: well-known citation]**. ePCR needs immutable per-field change history (who, what, when, device), access logs (who viewed which PCR), and amendment/addendum tracking. Under the 4-year retention for (b)(6) documentation and state retention rules, audit logs need equivalent retention.
- **42 CFR Part 2:** The updated rule's compliance date was **Feb 16, 2026**. Part 2 applies to federally assisted SUD *programs*. A typical 911 EMS agency is generally **not** a Part 2 program, but it may **receive** Part 2 records (e.g., from SUD treatment facilities in interfacility transfers, or via HIE) and must respect redisclosure restrictions. **[C for date; U for EMS applicability]** Sources: [HHS Part 2 final rule fact sheet](https://www.hhs.gov/hipaa/for-professionals/regulatory-initiatives/fact-sheet-42-cfr-part-2-final-rule/), [HIPAA Journal](https://www.hipaajournal.com/february-16-2026-compliance-deadline-part-2-final-rule/). **Implication:** Support record-level sensitivity tags and consent/redisclosure notices on records imported from external sources.
- **Record retention (state-specific):** Florida requires ePCR copies for ≥5 years ([Fla. Admin. Code 64J-1.014](https://www.law.cornell.edu/regulations/florida/Fla-Admin-Code-Ann-R-64J-1-014)). New Mexico requires minors' records for ≥10 years or 1 year past majority, whichever is longer ([NMAC 7.27.10.12](https://regulations.justia.com/states/new-mexico/title-7/chapter-27/part-10/section-7-27-10-12)). LA County keeps originals ≥7 years ([LA County](https://file.lacounty.gov/dhs/cms1_206280.pdf)). Washington uses state records retention schedules ([WA SOS advice sheet](https://sos.wa.gov/sites/default/files/2025-02/advice-sheet-which-retention-schedules-do-emergency-medical-services-%28ems%29-providers-use-%28december-2020%29.pdf)). Ohio has an EMS records rule ([OAC 4766-5-05](https://codes.ohio.gov/assets/laws/administrative-code/authenticated/4766/0/5/4766-5-05_20260501.pdf)). Public agencies also face public records retention schedules. Medicare claim documentation retention is commonly cited as 7+ years; for (b)(6) documentation it is ≥4 years. **[C for cited states; others U]** **Implication:** A per-tenant retention policy engine (by record type, patient age at service, jurisdiction), legal hold, and no hard-delete of clinical records before expiry.
- **State EMS data confidentiality:** Many states make PCR data submitted to the state confidential or privileged by statute (and QA data peer-review protected). **[U: not verified per-state this session]**
- **Fire records:** NERIS incident data is largely public (USFA publishes a public dataset, [USFA blog](https://www.usfa.fema.gov/blog/neris-public-transparent-fire-incident-data/)). Fire RMS records are generally public records subject to FOIA with PHI redaction. EMS PHI should be kept out of the fire incident record, or segregated. **[P]**

## 6. Key architecture and data-model implications for SomaOS

1. **Canonical incident hub:** CAD incident leads to (a) one NERIS incident (fire obligation) and (b) N NEMSIS PCRs (one per patient per unit), with shared times/address/units and enter-once mapping to both standards.
2. **Standards-as-configuration:** Build an element registry generated from the official NEMSIS v3.5.1 data dictionary/XSD plus NERIS OpenAPI schemas. Layer national, state (StateDataSet + state schematron + plus-one codes), region/LEMSA and agency, all effective-dated and versioned. Store the standard version and CP build on every record.
3. **Value semantics:** Every element supports value, NOT values, Pertinent Negatives, provenance (manual/CAD/device/AI) and per-row UUIDs for repeating groups.
4. **Validation engine:** Execute the official schematron (Saxon/SaxonJS) server-side, plus an offline client rule engine for protocol-driven required fields. Use tiered severities (block / warn / QA flag).
5. **Offline-first tablet client:** Encrypted local DB, outbox, cached config, row-level merge with single-author lock, post/lock then amendment model, visible sync state, MDM/remote wipe.
6. **Submission services:** A NEMSIS SOAP client (SubmitData/RetrieveStatus) with a per-state endpoint registry and resubmit-on-amend. A NERIS REST client (OAuth client credentials) with a multi-tenant enrollment model, entity/station/unit sync, and create plus update. A status dashboard and backlog/bulk-submit tooling.
7. **Certifications (gating):** NEMSIS v3.5.1 Collect Data compliance (90-day window, 2-year renewal), per-state vendor approval, and the NERIS Compatibility Badge.
8. **Device integration:** Partner-gated (ZDPP, LIFEPAK SDK/LIFENET). Cloud-pull, match-by-serial+time, crew-accept staging, 12-lead attachments. Deprioritize Philips in the US.
9. **Signatures and billing-grade data:** Typed, immutable, version-bound signatures (424.36 (b)(6) crew statement + facility rep), refusal/AMA workflow, PCS/ABN capture, loaded mileage in tenths, origin/destination modifiers, level-of-service and condition codes. NEMSIS XML export to billers; 837P later.
10. **Compliance:** BAA chain, encryption at rest and in transit plus MFA (meeting the pending Security Rule), field-level audit trail plus access logs, a jurisdiction-aware retention engine with legal hold, Part 2 sensitivity tagging, and segregation of public fire data from EMS PHI.
11. **HIE:** PDF plus FHIR/IHE mPSC-aligned bundle for the hospital "File" step. Later, Reconcile outcomes (eOutcome) via FHIR, and EMPI matching.
